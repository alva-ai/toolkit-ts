# feat: the /api/v2 transport for Toolkit 1.0

Primary record: alva-gateway/docs/changelogs/2026-11-19-agent-api-permissions.md
(D10 conventions, D16 IDs, R16, 4.2 and 4.6 M20). Rule text:
alva-gateway/doc/api-v2-conventions.md.

## 1. Background and Current State

- Toolkit 0.36.0 calls `/api/v1` REST routes and GraphQL through
  `AlvaClient._request`, which reads the v1 error envelope
  `{"error": {"code", "message"}, "details"}` and never retries (steward's
  pending read is the one bounded, immediate retry).
- The gateway now serves `/api/v2` (P2, one domain at a time): camelCase JSON,
  `{items, nextPageToken}` lists with `pageSize` and `pageToken`, repeated
  query parameters for lists, JSON Merge Patch on PATCH, RFC 9457 problems
  with `code`, `requiredPermission`, `invalidParams` and `retryAfter`, an
  `Idempotency-Key` that routes mirroring an `idempotencyKey` mutation
  require, and D16 IDs (`task_0…`) that clients treat as opaque strings.
- The gateway's authentication middleware still writes the v1 envelope on
  `/api/v2` (invalid API key, banned account) before a route's problem
  writer runs.
- M20 moves every Toolkit resource to `/api/v2` in a 1.0.0 major release
  whose breaking change is the ID format (human decision); public method
  signatures and output otherwise stay as they are (R16).

## 2. Behavior

- B1: `client._v2Request(method, path, options)` sends to
  `{baseUrl}/api/v2{path}` with the credential, analytics and origin-session
  headers `_request` sends, and the same timeout, abort and network-error
  handling.
- B2: query parameters skip `undefined` and `null` and repeat a parameter per
  array element (`?status=A&status=B`).
- B3: a JSON body is `application/json`; on PATCH it is
  `application/merge-patch+json`, and `null` members are sent (they clear).
- B4: every non-GET request carries an `Idempotency-Key`: the caller's key,
  unchanged on every attempt of one logical write, or a new UUID per call.
- B5: a failed response becomes an `AlvaError`: from a problem, `code`,
  `status`, `message` (detail, else title) and, when present,
  `requiredPermission`, `invalidParams` and `retryAfter` (the problem's, else
  the `Retry-After` delta-seconds); from the v1 envelope, as `_request` reads
  it; from any other body, `UNKNOWN` with the status and body text. Errors
  without these members do not gain the properties.
- B6: `client._v2Pages(path, options)` yields pages, sending `pageSize`, the
  list's other parameters and the previous `nextPageToken`, until the token is
  null or empty; `collectAll` returns their items in order. A response that is
  not a page, or that repeats the token it was sent, is `INVALID_RESPONSE`.
- B7: `v2Path` percent-encodes each interpolated value as one segment and
  refuses an empty, `.` or `..` value.
- B8: the CLI's error JSON adds `requiredPermission`, `invalidParams` and
  `retryAfter` when the error has them; other errors print as before.
- F1: `_request` and every resource behave as before; no resource moves here.

## 3. Decision

- D1: one transport method beside `_request`, sharing its header and fetch
  code (`_headers`, `_send`, `decodeResponse`), so both doors keep one
  credential, timeout and network-error path.
- D2: no new automatic retries (the record: Toolkit does not retry). The
  Idempotency-Key makes the retries that exist safe: a resource method that
  takes a request ID passes it as `idempotencyKey`, and an agent retrying the
  same command reuses it. `retryAfter` is exposed for the one retrying caller
  (steward) to use when it moves.
- D3: the new `AlvaError` members are optional and assigned only when
  present (declared fields), keeping the shape of every other error and the
  CLI output of v1 errors.
- D4: `details` stays undefined for a problem: its members are all mapped,
  and the problem carries no backend reason.
- D5: the v1 envelope is still read on `/api/v2`, because the gateway's
  authentication middleware writes it there.
- D6: `AlvaId` (`string`) is the public ID type. Each resource's ID fields
  switch to it when that resource moves to `/api/v2`, so no type claims a
  string while its route still returns a number.
- D7: `generateRequestId` moves from the steward resource to the transport
  module, its one shared UUID source.

## 4. Implementation

- `src/platformApi.ts`: `V2Method`, `Query`, `V2RequestOptions`, `Page`,
  `V2PageOptions`, `encodeQuery`, `v2Path`, `generateRequestId`,
  `v2ResponseError`, `collectAll`.
- `src/client.ts`: `_v2Request`, `_v2Pages`; `_request` split into
  `_headers`, `_send` and `decodeResponse` without a behavior change.
- `src/error.ts`: `InvalidParam`, `ProblemFields`, the three `AlvaError`
  members, `alvaErrorOutput` (the CLI's error JSON).
- `src/types.ts`, `src/index.ts`: `AlvaId`; exports `InvalidParam`,
  `ProblemFields`, `Page`.
- `src/cli/index.ts`: prints `alvaErrorOutput`.
- `src/resources/steward.ts`: imports `generateRequestId`.
- `README.md` (Migrating from 0.x to 1.0, Error Handling), `CHANGELOG.md`
  (new; 1.0.0 skeleton, completed as resources move).

## 7. Deviations and open points

- `package.json` stays at 0.36.0: `scripts/release.sh major` bumps it to
  1.0.0 at release, and a pre-bumped 1.0.0 would release as 2.0.0
  (`2026-11-16-thesis-watchpoints.md` took the same course).
- The repository had no `CHANGELOG.md`; this change creates it for the 1.0
  notes (record 4.8).
- Browser and PBSV callers: `/api/v2` sends no CORS allowance and treats a
  PBSV as a guest. Settled in section 8: `fs`, Playbook and Skillhub
  discovery and the UDF runtime keep `/api/v1` for clients without an API
  key (`AlvaClient._sendsApiKey`).

- Review (M20 client review, 2026-11-19): every `/api/v2` request the suite
  sends was checked against the final gateway contract,
  `pkg/v2/api/testdata/v2_snapshot.golden` at alva-gateway `b34005a9`. A
  vitest setup file (scratch, not committed) recorded each `_v2Request` with
  its call site; a script matched method and path to a route, every query
  parameter and body field (with its type and enum value) to the route's
  request fields, and every ID path parameter, query and body ID to its
  declared type's prefix. 620 calls on 145 routes; every `_v2Request` call
  site in `src/` ran at least once. The only mismatches were the synthetic
  routes of `test/platformApi.test.ts`. The fake responses were checked the
  same way against the routes' response fields: the only extra fields are in
  tests that feed a malformed response on purpose (and a `visibility` the
  company-news CLI test returns but nothing reads). Every property of the
  `Wire*` types and of the inline response types exists in the snapshot.
- R1 (fixed, `d1e3582`): an agent could no longer link a Thesis. The Alva
  App's Thesis card and the `alva.ai/thesis/<id>` page take the Thesis
  number (feed-app `thesis-link.ts` accepts only digits, the detail read is
  `playbook:<number>`), which 0.x returned as the ID; 1.0 returned only D16
  IDs. Thesis outputs now carry `number` and `author_version_number`, and
  publication summaries `thesisNumber`, read from the `/api/v2` `number`
  fields (the legacy Thesis and author version IDs, `convert.go`).
  Falsified: the version number taken from the current version, the Thesis
  number, the summary number and the number validation, each failed a test.
- Review verification: `npm run lint`, `npm run format:check`,
  `npm run typecheck`, `npm test` (75 files, 1,499 tests, `fetch` disabled

## 8. Integration (Toolkit 1.0.0)

The resources moved in three slices, each with its own changelog, then were
cherry-picked onto this branch in order:

- [content](2026-11-19-content-resources-v2.md): Theses, Thesis reads, For
  You, Playbooks, release, feeds, comments, remix, Skillhub, SDK docs.
- [social, automation, files, account](2026-11-19-agent-api-v2-social-automation-files-account.md).
- [market, trading, billing, functions, runtime](2026-11-19-agent-api-v2-market-trading-runtime.md).

Conflicts were in `test/resources/resources.test.ts` (each slice moved or
deleted different blocks; every block a slice removed stays removed),
`test/cli.test.ts` (the embedded producer ID is a Cronjob ID), and the
`CHANGELOG.md` and README lists (kept from every slice, then rewritten).

Integration changes:

- I1: one caller-username read. The slices had three (`client.user._username()`,
  a `callerUsername` WeakMap in `playbooks.ts`, an uncached `GET /me` in
  `trading.subscribe`). Release, own-Playbook lookups and copy trading now use
  `client.user._username()`, which reads only `username`, so a client reads
  `GET /api/v2/me` once.
- I2: one API-key door. `fs` and the Playbook/Skillhub discovery each
  decided when to fall back to `/api/v1`; both now ask
  `AlvaClient._sendsApiKey()` (API key present and no PBSV or viewer token,
  which `_headers` sends first).
- I3: `functions register` shares deploy's `--run-as-service-account` check
  after refusing `--clear-run-as`, so `0` (the 0.x clear) and blank values are
  refused; the slice's own check let `0` through to the server.
- I4: `alva run` help names `/api/v2/runs`, the `feed` and `playbooks` help
  examples use platform IDs, and the README For You, Playbook
  Functions, Company News and browser sections drop `newerThan`, numeric
  IDs and `POST /query`.
- I5: `CHANGELOG.md` 1.0.0 is complete: general breaking changes (IDs,
  errors, permissions, browser credentials), per-area changes, additions and
  the calls still on `/api/v1`; the README migration section matches it.

Calls still outside `/api/v2` (grep of `src/` for `/query`, `/api/v1` and
`fetch(`, 2026-11-19):

- GraphQL `/query`: `steward.ts` only (blocks M21).
- `/api/v1` REST, no `/api/v2` route: `trading.execute` and
  `subscribe({executeLatest: true})`; `notifications.listFeed`,
  `subscriptions.subscribeFeed`/`unsubscribeFeed`; `secrets.get`;
  `channelGroupSubscriptions` context/list/subscribe/unsubscribe.
- `/api/v1` by credential: `fs`, `playbooks` discovery and `playbookSkills`
  without an API key; `playbookRuntime.ts` (`/api/v1/service/invoke`,
  `/service/functions`).
- Not the platform API: `auth login`'s `/api/v1/oauth/token` (record: OAuth
  stays v1) and `dataSkills` (the Arrays service, `arraysBaseUrl`);
  `skillEndpoints.ts` is static metadata.

Open questions (decided, to review):

- I1 reads `GET /me` once per client and caches it for the client's life;
  a username rename during a long-lived client keeps the old name (the
  slices' caches did the same).
- I2 sends a client with both an API key and a PBSV token to `/api/v1`
  everywhere, because `_headers` sends the PBSV; the alternative (prefer the
  key on `/api/v2`) would change which identity a browser Playbook acts as.
- I3 refuses `--run-as-service-account 0` on `functions register` as a usage
  error rather than letting `/api/v2` reject it, matching deploy.
